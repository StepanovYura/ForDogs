# NIXDOG STUDIO — интернет-магазин одежды для собак

Стек, как в задании:

| Слой | Что используется |
|---|---|
| Фронтенд и бэкенд | **Next.js 14** (App Router), деплой на **ONREZA** |
| База данных | **PostgreSQL** — ONREZA Managed PostgreSQL |
| ORM | **Prisma** |
| Файлы и картинки | **Yandex Object Storage** (S3-совместимое API) |
| Платежи | **Т-Банк**: банковская карта и «Долями» (страница банка), **СБП** (динамический QR) |
| SSL | автоматический сертификат ONREZA |
| Исходники | **GitHub** |

Отдельного бэкенд-сервера нет и не нужно: в Next.js серверная часть живёт
рядом с фронтендом — это серверные компоненты, server actions и route
handlers в `app/api/`. Prisma работает только на сервере, в браузер ничего
из неё не попадает.

---

## Что уже умеет сайт

**Без входа:** главная с обложкой на весь экран, каталог с поиском и
фильтрами (категория, цена, цвет, размер, наличие, сезон, назначение,
коллекция) и сортировкой, избранное, карточка товара с галереей, выбором цвета и размера, таблицей размеров и раскрывающимися
блоками, корзина, страницы «О бренде», «Доставка», «Контакты», «Как выбрать
размер».

**После входа:** оформление заказа с адресом доставки, оплата по QR-коду СБП,
личный кабинет с профилем и историей заказов.

**Администратору:** сводка по выручке и остаткам, все заказы со сменой
статуса, обложка главной (раздел «Главная»), метки для фильтров — сезоны,
назначения, коллекции (раздел «Фильтры»), управление товарами — создание, редактирование, цвета и размеры с
остатками, загрузка фотографий в Yandex Object Storage, удаление.

Остатки списываются в момент создания заказа и возвращаются обратно, если
оплата не прошла или заказ отменили. Цены при оформлении берутся из базы, а
не из браузера, — подменить сумму со стороны клиента нельзя.

## 1. База данных: ONREZA Managed PostgreSQL

1. В панели ONREZA создайте инстанс **Managed PostgreSQL**.
2. Скопируйте из панели **две** строки подключения — там есть готовые
   примеры, ничего дописывать руками не надо:
   - режим **Pooled** (через PgBouncer, хост с суффиксом `-pooler`) →
     в `DATABASE_URL`. Через него идут все запросы сайта.
   - режим **Direct** (тот же хост без `-pooler` и без параметров
     `pgbouncer` / `connection_limit`) → в `DIRECT_URL`. Он нужен Prisma
     для `db:push`, `migrate` и `db:seed`: через PgBouncer в
     transaction-режиме эти команды не отрабатывают. В `schema.prisma`
     за это отвечает поле `directUrl`.

   Домен у обоих — `*.kaiki.onreza.ru`. Если в строке оказался просто
   `*.kaiki.ru`, это другой сервер: имя резолвится, но базы там нет, и
   Prisma ответит `P1001: Can't reach database server`.
3. Положите её в `DATABASE_URL` (локально в `.env`, на проде — в
   переменные окружения проекта в ONREZA).

> **Важно:** если строка подключения от ONREZA уже заканчивается на
> `?sslmode=require`, второй раз его дописывать не надо — два знака `?` в
> одном адресе ломают разбор параметров.

> **Где хранить переменные локально.** Файл должен называться именно `.env`.
> Next.js читает и `.env`, и `.env.local`, а вот Prisma CLI (`db:push`,
> `db:seed`, `migrate`) видит **только `.env`** — если положить настройки в
> `.env.local`, Prisma скажет `Environment variable not found: DATABASE_URL`.
> Оба файла в `.gitignore`, в репозиторий не попадут.

Схема базы описана в `prisma/schema.prisma`. Применить её:

```bash
npm run db:push     # создаёт таблицы по схеме (быстрый путь для старта)
npm run db:seed     # наполняет каталог и создаёт администратора
```

Когда проект уедет в прод и схема начнёт меняться, переходите на миграции:

```bash
npx prisma migrate dev --name init     # локально: создаёт файл миграции
npm run db:migrate                     # на проде: применяет миграции
```

У ONREZA есть ветвление базы — можно завести отдельную ветку под preview и
проверять изменения схемы, не трогая боевые данные.

## 2. Yandex Object Storage: фотографии товаров

1. В консоли Yandex Cloud создайте бакет, например `nixdog-media`, и
   поставьте ему **публичный доступ на чтение объектов**.
2. Создайте сервисный аккаунт с ролью `storage.editor` и выпустите ему
   **статический ключ доступа** — получите пару `ключ / секрет`.
3. Впишите их в `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`, бакет — в
   `S3_BUCKET`.
4. В настройках CORS бакета разрешите метод `PUT` с домена вашего сайта —
   иначе браузер не сможет загрузить файл напрямую в хранилище:

```json
[
  {
    "AllowedMethods": ["GET", "PUT", "POST", "HEAD"],
    "AllowedOrigins": [
      "https://nixdog-studio-yurastep05-pnp4.onreza.app",
      "http://localhost:3000"
    ],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

Три места, где легко ошибиться:

- **`AllowedOrigins` — это адрес сайта, а не бакета.** Он должен совпадать
  с тем, что стоит в адресной строке, буква в букву: протокол `https`,
  тот же домен, без слэша в конце и без пути.
- **`AllowedHeaders` оставьте `["*"]`.** Подписанная ссылка несёт служебные
  заголовки (`x-amz-acl` и другие), и если их не разрешить, браузер
  остановит запрос ещё на предварительной проверке.
- **Правило применяется не мгновенно** — дайте минуту и обновите страницу
  с очисткой кэша (Ctrl+F5), браузер кэширует ответ предварительной проверки.

Проверить, что адрес сайта действительно попал в правило, можно командой
`node check-storage.mjs` — пятый пункт её вывода как раз про это.

Как это работает: админка просит у сервера временную подписанную ссылку
(`/api/admin/upload-url`), браузер отправляет файл **прямо в хранилище**, и
только потом сообщает серверу URL (`/api/admin/attach-image`). Файл не
проходит через Next.js, поэтому нет ограничения на размер запроса.

## 3. Оплата: СБП и банковская карта

Покупатель оформляет заказ — сайт резервирует товары и просит у банка
**динамический QR-код СБП** на сумму заказа. Дальше на странице заказа:

- **на компьютере** — QR-код: его сканируют камерой телефона или в
  приложении банка;
- **на телефоне** — кнопка «Оплатить в приложении банка»: ссылка из QR
  открывает список банков, покупатель выбирает свой и подтверждает платёж;
- таймер жизни QR (по умолчанию 15 минут, `SBP_QR_TTL_MINUTES`) и
  кнопка «Отменить заказ».

Страница сама раз в 3 секунды спрашивает сервер о статусе и сразу
показывает «Оплата прошла», как только банк подтвердил платёж.

Если QR истёк, сайт отзывает его у банка, отменяет заказ и возвращает
товары на склад. Брошенные заказы закрываются при следующем оформлении
заказа и при открытии админки заказов. Если деньги всё же пришли уже после
отмены, админка подсветит такой заказ — нужен возврат или ручное
восстановление.

Уведомлению банка на слово не верим: получив его, сервер сам перезапрашивает
статус платежа в API банка и меняет заказ только по ответу API.

### Как устроен код

```
lib/payments/index.js   — вся логика оплаты; сайт работает только с ним
lib/payments/mock.js    — эмулятор банка для разработки
lib/payments/tbank.js   — адаптер Т-Банка (интернет-эквайринг: карта + QR СБП)
lib/payments/sber.js    — адаптер Сбера (запасной вариант)
lib/orders.js           — «оплачен» / «отменён + вернуть остатки», атомарно
app/order/[id]/         — страница заказа с QR-кодом
app/api/orders/[id]/payment/       — статус оплаты (GET) и отмена (DELETE)
app/api/payments/<банк>/webhook/   — уведомления от банка
app/dev/bank/[id]/      — «банк» эмулятора (QR и оплата картой)
```

Какой банк выдаёт QR, задаёт `PAYMENT_PROVIDER`. Подключение банка —
это один файл-адаптер в `lib/payments/` и одна строка в списке `PROVIDERS`
в `lib/payments/index.js`; оформление заказа и страницу оплаты трогать
не нужно. Что должен уметь адаптер, описано в начале `lib/payments/index.js`.

### Эмулятор банка (локальная разработка)

Пока банк не выбран, работает `PAYMENT_PROVIDER=mock`. QR-код ведёт на
страницу `/dev/bank/...` этого же сайта — там платёж можно оплатить или
отклонить, и эмулятор пришлёт уведомление на вебхук так же, как банк.
Деньги не списываются.

В боевой сборке (`npm run build && npm start`, ONREZA) эмулятор выключен:
иначе любой мог бы «оплатить» заказ кнопкой. Чтобы показать оплату
заказчику на тестовом стенде, его можно включить явно —
`SBP_MOCK_IN_PRODUCTION=1`. На боевом сайте так делать нельзя.

### Т-Банк: интернет-эквайринг

**Интернет-эквайринг** — договор с банком на приём оплат на сайте. Банк
выдаёт «терминал» — ключ (`TerminalKey`) и пароль для API: сначала
тестовый, после проверки сайта — боевой. Сайт через терминал создаёт
платежи, банк принимает деньги картой или по СБП и зачисляет их на
расчётный счёт заказчика за вычетом комиссии. Со стороны сайта всё готово:
адаптер `lib/payments/tbank.js` (карта на платёжной странице Т-Банка + QR
СБП на странице заказа).

Порядок подключения:

1. **Заказчик** подаёт заявку на интернет-эквайринг в Т-Бизнесе (нужен
   расчётный счёт ИП/ООО; СБП и карты — в одной заявке). Указывает адрес
   сайта.
2. **Мы**: в кабинете Т-Бизнеса → Интернет-эквайринг → Магазины берём
   **тестовый терминал** (ключ оканчивается на `DEMO`), прописываем в `.env`:
   `PAYMENT_PROVIDER=tbank`, `TBANK_TERMINAL_KEY`, `TBANK_PASSWORD`.
   В настройках терминала указываем:
   - способ уведомлений — **HTTP**, адрес
     `https://ваш-домен/api/payments/tbank/webhook`;
   - адреса успеха и ошибки можно не заполнять — сайт передаёт их сам.
3. Проходим **тестовые сценарии** из кабинета Т-Банка (успешная оплата,
   отказ, отмена, СБП) — кабинет показывает, какие пройдены.
4. **Проверка сайта банком** (см. ниже) → банк выдаёт **боевой терминал**,
   меняем ключ и пароль в переменных ONREZA.

### Оплата «Долями»

«Долями» — сервис оплаты частями от Т-Банка: покупатель платит 25%
сразу и ещё три раза по 25% каждые две недели, без переплат. Магазин
получает всю сумму сразу, комиссию за сервис платит магазин (её размер
— в договоре).

Подключается к тому же терминалу интернет-эквайринга: покупатель выбирает
«Долями» при оформлении заказа и уходит на платёжную страницу Т-Банка,
где оформляет оплату частями. Сайт, как и для карты, ждёт подтверждения
банка и перепроверяет статус сам. В карточке товара показывается
«4 платежа по … ₽ с «Долями»».

Что сделать:
1. **Заказчик** просит менеджера Т-Банка подключить «Долями» к терминалу
   интернет-эквайринга и уточняет пределы суммы заказа.
2. **Мы** прописываем `PAYMENT_DOLYAME_ENABLED=1` и, если есть пределы,
   `DOLYAME_MIN_RUB` / `DOLYAME_MAX_RUB`. Вне пределов способ не
   предлагается ни при оформлении, ни в карточке товара.
3. Проверяем на тестовом терминале, что на платёжной странице Т-Банка
   есть вариант «Долями».

Чек по 54-ФЗ при «Долями» формируется так же, через `Receipt` в платеже.

### Что банк проверяет на сайте

Перед выдачей боевого терминала менеджер банка открывает сайт. На сайте
уже есть всё, что обычно требуют, — осталось заполнить данные:

| Что | Где на сайте | Что сделать |
|---|---|---|
| Реквизиты продавца (ИП/ООО, ИНН, ОГРН, адрес) | подвал, «Контакты», оферта | «Админка → Реквизиты и соцсети» |
| Контакты: почта, телефон | «Контакты», подвал | там же |
| Публичная оферта | `/offer` | показать юристу, сверить условия возврата и доставки |
| Политика обработки персональных данных | `/privacy` | показать юристу |
| Согласие на обработку данных | галочка при оформлении заказа и регистрации | — |
| Условия доставки и возврата | `/delivery` | проверить сроки и цены доставки |
| Цены в рублях, описания товаров | каталог, карточки | заполнить товары |
| Логотипы платёжных систем | подвал | текстовые значки; если банк попросит, заменить на официальные логотипы из набора Т-Банка |
| HTTPS | весь сайт | ONREZA выпускает сертификат сам |

Пока реквизиты не заполнены, в оферте и политике на их месте видна
пометка «не заполнено» — чтобы сайт случайно не ушёл на проверку
недоделанным. Ссылку отправляем менеджеру банка, когда сайт работает на
своём домене на ONREZA.

Кроме того, заказчик как **оператор персональных данных** должен подать
уведомление в Роскомнадзор (pd.rkn.gov.ru) — это делается один раз
онлайн.

### Онлайн-касса и чеки (54-ФЗ)

Связка работает так:

```
Покупатель платит → Т-Банк принимает оплату
                  → Т-Банк передаёт чек (Receipt из нашего платежа) в онлайн-кассу
                  → касса пробивает чек → ОФД передаёт его в налоговую
                  → покупатель получает чек на почту / по СМС
```

Со стороны сайта всё готово: с каждым платежом в Т-Банк уходит чек —
товары, цены по размерам, количество, почта и телефон покупателя
(`TBANK_RECEIPTS=1`).

**Что нужно от заказчика:**
1. **Онлайн-касса.** Самое простое — облачная касса, подключаемая к
   эквайрингу Т-Банка прямо в кабинете Т-Бизнеса (собственная касса банка
   или партнёры: АТОЛ Онлайн, CloudKassir, OrangeData, Бизнес.Ру и др.).
   Касса арендуется вместе с фискальным накопителем, физически ничего
   ставить не нужно.
2. **Регистрация кассы в ФНС** — через сервис кассы, понадобится
   квалифицированная электронная подпись (КЭП) ИП или директора.
3. **Договор с ОФД** (оператором фискальных данных) — обычно идёт в пакете
   с облачной кассой.
4. **Бухгалтер** называет систему налогообложения и ставку НДС.

**Что нужно от нас:**
1. Прописать `TBANK_RECEIPTS=1`, `TBANK_TAXATION` (например `usn_income`),
   `TBANK_VAT` (например `none`) и `TBANK_FFD_VERSION` (версию ФФД скажет
   сервис кассы) в переменных ONREZA.
2. Сделать тестовую покупку и найти чек в кабинете ОФД.

Если заказчик — **самозанятый**, касса не нужна: Т-Банк умеет формировать
чеки через «Мой налог», это включается в кабинете Т-Бизнеса.

### Письма о заказах

Сайт сам отправляет письма покупателю — «оплачен», «передан в доставку»
(с трек-номером из админки), «вручён», «отменён» — и администратору о
каждом новом оплаченном заказе. Код — `lib/notifications.js` (шаблоны) и
`lib/mail.js` (отправка).

Отправка идёт по **SMTP** — подходит любой почтовый сервис:

- **Яндекс 360 / Mail.ru для бизнеса** — ящик на домене магазина
  (`shop@домен`), самый простой вариант для небольшого магазина;
- **Unisender, SendPulse** и подобные — если писем станет много или нужны
  рассылки и статистика доставки.

Что сделать: завести ящик (или аккаунт сервиса), в настройках безопасности
создать **пароль приложения** и прописать `SMTP_HOST`, `SMTP_PORT`,
`SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, `ADMIN_EMAIL` (см.
`.env.example`). Чтобы письма не попадали в спам, у домена настраиваются
записи SPF и DKIM — почтовый сервис даёт готовые значения для DNS.

Пока SMTP не настроен, письма при локальной разработке сохраняются HTML-
файлами в папку `.outbox` — их можно открыть в браузере и посмотреть.

Чеки по 54-ФЗ приходят покупателю **отдельно** — от ОФД или кассы, — в
наших письмах их нет.

### Сбер (запасной вариант)

Если вернётся Сбер: адаптер `lib/payments/sber.js` работает с его
платёжным шлюзом (интернет-эквайринг) и оплатой по динамическому QR СБП.
Все настройки — переменные `SBER_*` в `.env.example`.

1. Подключить в Сбере **интернет-эквайринг с оплатой через СБП** и получить
   доступ к **тестовому стенду**: логин и пароль API-пользователя.
2. Прописать их в `.env`, поставить `PAYMENT_PROVIDER=sber` и пройти
   оплату на тестовом стенде. Сверить с менеджером Сбера:
   - доступен ли метод `sbp/c2b/qr/dynamic/get.do` (QR СБП) для договора;
   - включён ли «динамический callback» (`SBER_DYNAMIC_CALLBACK`), иначе
     адрес уведомлений прописывается в кабинете:
     `https://ваш-домен/api/payments/sber/webhook`;
   - симметричный ключ для подписи уведомлений → `SBER_CALLBACK_SECRET`.
3. Для боевого режима: боевые логин и пароль и
   `SBER_API_URL=https://securepayments.sberbank.ru/payment/rest`.

### Оплата картой

Второй способ оплаты — банковская карта (Visa, Mastercard, МИР). Покупатель
выбирает его при оформлении заказа, и сайт отправляет его на **платёжную
страницу Сбера**: там он вводит карту и проходит 3-D Secure, после чего банк
возвращает его на страницу заказа. Статус сайт, как и для СБП, перепроверяет
запросом в банк.

**Почему карта вводится не на нашем сайте.** Сайт, через который проходят
номера карт, обязан соответствовать стандарту PCI DSS — с ежегодным аудитом,
сканированием уязвимостей и отдельной инфраструктурой. Банк без этого не
разрешит принимать карты в своей форме. При оплате на странице банка данные
карты не попадают ни на наш сервер, ни в нашу базу, ни в логи — украсть их у
нас нечего (это самый лёгкий уровень PCI DSS — SAQ A). Так работает
подавляющее большинство интернет-магазинов. Если нужна страница оплаты «в
стиле магазина», Сбер умеет настраивать оформление своей платёжной страницы
— это обсуждается с менеджером, код сайта менять не придётся.

Что ещё сделано для безопасности:
- сайт запрещает встраивать себя в чужие страницы (защита от подмены
  кнопки «Оплатить»), браузер ходит на него только по HTTPS, адреса страниц
  заказа не передаются чужим сайтам — заголовки в `next.config.js`;
- сумма заказа берётся из базы, а не из браузера; уведомлениям банка сайт
  не верит на слово и перепроверяет статус запросом в банк.

Карту можно временно выключить переменной `PAYMENT_CARD_ENABLED=0` —
останется только СБП.

## 4. Запуск локально

Нужен Node.js 18.17 или новее и Docker Desktop.

Локальная разработка идёт на **своей** базе в контейнере — боевая база в
ONREZA при этом не затрагивается совсем. Это заодно обходит проблему, с
которой можно столкнуться дома: некоторые провайдеры и антивирусы рвут
подключения к базам данных по сети. Соединение внутри компьютера такой
фильтрации не подлежит.

```bash
npm install
npm run db:up        # поднять базу в контейнере
npm run db:push      # создать таблицы по схеме
npm run db:seed      # залить демо-каталог и администратора
npm run dev
```

Сайт откроется на http://localhost:3000, вход в админку — по значениям
`SEED_ADMIN_EMAIL` и `SEED_ADMIN_PASSWORD` из `.env`.

Дальше правки в файлах видны в браузере сразу при сохранении — ни сборки,
ни деплоя для этого не нужно.

### Управление локальной базой

```bash
npm run db:up      # запустить
npm run db:down    # остановить (данные сохраняются)
npm run db:reset   # снести вместе с данными и поднять пустую
npx prisma studio  # посмотреть и поправить данные в браузере
```

Контейнер отдаёт базу на порт **15432**, а не на привычный 5432.

Если увидите ошибку `P1000` или `28P01` — «неверный пароль», хотя пароль
верный, — почти наверняка на этом порту сидит другая программа, говорящая
на протоколе PostgreSQL, и отвечает вместо контейнера. Docker при этом
ошибки не покажет: он занимает «все адреса», а обращения на `127.0.0.1`
достаются тому, кто занял именно этот адрес. Проверить, кто занял порт:

```powershell
netstat -ano | findstr :15432
Get-Process -Id НОМЕР_ИЗ_ПОСЛЕДНЕЙ_КОЛОНКИ
```

Лечится сменой порта в `docker-compose.yml` и в обеих строках подключения
в `.env`.

### Что где лежит

`.env` описывает окружение на вашем компьютере: база локальная, адрес сайта
`http://localhost:3000`. Боевые настройки живут в панели ONREZA, в
репозиторий не попадают и в `.env` не дублируются; прежнее содержимое файла
сохранено рядом как `.env.prod-backup` — он в `.gitignore`.

Ключи Object Storage в локальном `.env` те же, что на проде. Это сделано
намеренно: в правилах CORS бакета уже разрешён
`http://localhost:3000`, поэтому загрузка фотографий работает и локально.
Но имейте в виду — **залитые с локальной машины файлы попадают в боевой
бакет**. Если это мешает, заведите отдельный бакет для разработки и
поменяйте `S3_BUCKET` в `.env`.

## 6. Деплой на ONREZA

1. Подключите GitHub-репозиторий в панели ONREZA — фреймворк Next.js
   определится автоматически, Dockerfile писать не нужно.
2. В разделе переменных окружения добавьте всё из `.env.example`:
   `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`, `SEED_ADMIN_EMAIL`,
   `SEED_ADMIN_PASSWORD`, `PAYMENT_PROVIDER` и ключи банка, `SBP_QR_TTL_MINUTES`,
   `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
   `S3_SECRET_ACCESS_KEY`, `NEXT_PUBLIC_SITE_URL`.
3. **Первый деплой** — укажите команду сборки:

   ```
   npm run db:setup && npm run build
   ```

   `db:setup` создаёт таблицы по схеме и наполняет каталог, `build` собирает
   сайт. Сборка идёт внутри ONREZA, рядом с базой, поэтому домашний интернет
   и его фильтры тут ни при чём.

4. **После того как первая сборка прошла — верните обычную команду:**

   ```
   npm run build
   ```

   Иначе схема будет пересобираться при каждом деплое. Повредить данным это
   не должно (`db push` отказывается выполнять разрушающие изменения, а seed
   написан на upsert-ах и ничего не затирает), но лишняя работа на каждом
   пуше не нужна.

5. После первого деплоя пропишите реальный адрес в `NEXT_PUBLIC_SITE_URL`
   и пересоберите — из него собирается адрес вебхука для банка.
6. Привяжите домен: SSL-сертификат ONREZA выпустит и будет продлевать сам.

Когда схема начнёт меняться, переходите с `db push` на миграции: локально
`npx prisma migrate dev --name что-поменяли`, файл миграции коммитится в git,
а команда сборки на проде один раз меняется на
`npm run db:migrate && npm run build`.

Дальше каждый `git push` в `main` пересобирает и обновляет сайт.

## 7. Как сделать себя администратором

Ролей две: `USER` (у всех новых) и `ADMIN`. Отдельной кнопки «сделать
админом» нет намеренно — это слишком чувствительное действие.

Первый администратор создаётся при `npm run db:seed`. Чтобы повысить другого
пользователя, выполните SQL в базе:

```sql
UPDATE users SET role = 'ADMIN' WHERE email = 'почта@пользователя';
```

Или через Prisma Studio — удобная визуальная таблица:

```bash
npx prisma studio
```
